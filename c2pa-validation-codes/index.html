C2PA validation status codes

When a validator checks a file's Content Credentials, it reports each check as a status code: a success, an informational note or a failure. Version 2.5 of the C2PA specification (October 2026) defines 126 of them. Below: the ones you are most likely to meet, in plain words, then every code in the specification's own words.

Updated 22 November 2026

How c2paview turns codes into green, amber and red

  • Green: no failure codes, the signature validated (claimSignature.validated), and the signer is on the C2PA trust list or the older interim trust list (signingCredential.trusted, validation state Trusted).
  • Amber: the only failure is signingCredential.untrusted, so the file is intact but who signed it can't be confirmed; or the trust lists could not be loaded; or the checks did not come back conclusive either way.
  • Red: any other failure code. The result says which kind: content that no longer matches (a …Hash.mismatch), which means the file changed after signing; a problem with the credentials themselves, such as their signature; or a problem with the signer's certificate. A manifest the library calls Invalid without naming a failure is red too.

Informational codes never change the colour. Time-stamp problems are informational on purpose: the specification says a failed time-stamp "does not necessarily (by itself) cause the C2PA Manifest to be rejected", and the validator then carries on as if there were none. Identity codes (cawg.*) are listed with the identity they belong to, not in the file's verdict, though a failed identity check can stop the library reporting the manifest as Trusted, which leaves the verdict amber.

The specification sorts a manifest into three states: Well-Formed, Valid and Trusted. "Any Trusted manifest is also Valid, and any Valid manifest is also Well-Formed." The C2PA library c2paview uses reports Invalid, Valid or Trusted instead, with Invalid covering everything below Valid.

Questions

What does signingCredential.untrusted mean?

The signer's certificate does not lead back to any certificate on the trust lists the validator uses, so the name in it can't be confirmed. The file can still be intact and validly signed: if the other checks pass, the C2PA specification counts such a manifest as Valid, just not Trusted. When it is the only failure, c2paview shows it amber.

What does assertion.dataHash.mismatch mean?

The file's content no longer matches the hash recorded when it was signed: the bytes the signature covers have changed since, by editing, re-saving or damage. c2paview shows it red, as changed after signing.

What is the difference between Valid and Trusted?

In the C2PA specification, a Valid manifest is well-formed and has not been modified since it was signed, its signature validated and was made within the signing certificate's validity period, and that certificate has not been revoked. A Trusted manifest is all of that, and its signing certificate is on a trust list. The C2PA library c2paview uses reports Invalid for anything below Valid.
